# ADR-001：移除服务端的 `ComplianceRule.ConfirmFrames`

- 状态：已采纳
- 日期：2026-11-14

## 背景

`ComplianceRules` 表里有一个 `ConfirmFrames` 字段（默认 3），含义是"连续多少帧一致才采信"。
它能通过 `GET/PUT /api/devices/{id}/rule` 读写，前端也出现过相关类型。

但排查后发现：**这个字段从来没有生效过。**

| 位置 | 实际情况 |
|---|---|
| 服务端判定 `ComplianceEvaluator` | 只读取 `RequireMask` / `RequireHelmet` / `MinConfidence`，**完全不看 `ConfirmFrames`** |
| 设备端 `scripts/judge.py` | 自己写死了 `CONFIRM_FRAMES = 3`，**从不向服务端请求规则** |

也就是说：改服务端的这个值不会有任何效果，而设备端用的是它自己那份常量。
**两份配置各自存在，谁也不知道对方**，属于必然漂移的死字段。

## 为什么不在服务端实现它

"连续 N 帧"是一个**视频时序**概念。服务端收到的是 `DetectionReportDto`，
粒度是"一次上报一批结果"，没有帧的概念，也没有帧序号。

要在服务端实现，就得引入跨报文的计数状态（内存或 Redis），
还要处理多实例、超时、trackId 复用等问题——**为了一个本该属于边缘端的逻辑，引入分布式状态**。

## 决策

**删除服务端的 `ConfirmFrames` 字段**（实体、DTO、入参、数据库列），
把"连续 N 帧"的配置明确留在设备端。

同时更新 `scripts/judge.py` 的注释，说明这是设备端本地配置，不是服务端下发。

## 后果

- 服务端少了一个"看起来能配、实际不生效"的字段，消除了配置漂移的可能。
- 代价是**失去了远程调整帧数的能力**。
- 如果将来确实需要远程配置，正确做法是：新增一个**设备拉取配置**的接口
  （设备用 `deviceCode` + `ApiKey` 拉取），由设备在启动时应用——
  而不是在服务端做判定，也不是在服务端存一个没人读的字段。

## 备选方案（已否决）

| 方案 | 否决原因 |
|---|---|
| 服务端实现多帧确认 | 服务端没有帧概念；需要分布式状态；复杂度远高于收益 |
| 保留字段并注释"暂未使用" | 死字段就是死字段，注释不会让它生效，反而误导调用方 |

## 经验

**"字段存在"不等于"功能存在"。** 判断一个配置项是否真的生效，
唯一可靠的方法是搜索它的读取点，而不是看它的写入点。
